# Bug fixes

Журнал заметных багов и их фиксов (что сломалось, почему, как починили).

## 2026-08-18 — UnicodeEncodeError в save_status: третья точка входа cp1251

**Симптом.** На cp1251-машине (у коллеги; на машинах с включённой системной UTF-8 не
воспроизводится) нода падала сразу после «Start node»:

```
node.py, in save_status -> json.dump -> encodings\cp1251.py
UnicodeEncodeError: 'charmap' codec can't encode character '\u25b6' (▶) in position 1
```

**Причина.** Тот же класс, что и утренний баг с консолью, но не поток, а **файл**:
`save_status` писал `status.json` через `open(path, 'w')` без `encoding=` при
`ensure_ascii=False` — локальная кодировка cp1251 не знает `▶` из строки события раунда.
Фикс потоков (`_fix_std_streams`) файловые записи не покрывает.

**Фикс** — два слоя:

1. Явный `encoding='utf-8'` во всех текстовых `open()` поставляемого кода, где его не было:
   `node.py` (status.json — сам краш, node_id), `alphanode_gui.py` (gui_settings.json
   чтение/запись, **чтение status.json** — иначе GUI на cp1251 падал бы уже при чтении
   UTF-8-статуса с `▶`, node_id, лог сигнал-сервиса), `paper_trade.py` (state/trades).
2. Системная страховка: PyInstaller-опция `X utf8_mode=1` в `AlphaNode.spec` — весь
   замороженный процесс работает в Python UTF-8 mode (как Linux-сборки), и любой забытый
   `open()` без кодировки по умолчанию становится UTF-8. Selfcheck проверяет флаг
   (`utf8 mode : 1`) и валит сборку, если опция потеряется.

**Почему «у меня не воспроизводится»:** на машине разработчика включена системная
UTF-8 (cp65001, «Use Unicode UTF-8 for worldwide language support») — там локальная
кодировка и так UTF-8. У пользователей со стоковой русской Windows — cp1251.

## 2026-08-18 — Лидерборд «исчезает» при нехватке высоты окна

**Симптом.** Список найденных альф пропадает целиком (вместе с заголовком LEADERBOARD) —
между консолью и PORTFOLIO остаются только две ручки-разделителя. Счётчик «alphas found»
при этом растёт, `library.jsonl` в порядке.

**Причина.** Карточка лидерборда — единственная эластичная строка сетки дашборда
(`weight=1`). Когда фиксированные соседи (растянутая консоль + PORTFOLIO + FORWARD TRACK)
в сумме превышают высоту окна, Tk сжимает эластичную строку до 0 px — карточка визуально
исчезает, а нижняя карточка обрезается краем окна.

**Фикс** (`alphanode/alphanode_gui.py::_regrid_cards`): строке лидерборда задан
`minsize=220dp` (заголовок + несколько строк) — ниже этого её сжать нельзя; при дефиците
места теперь обрезаются нижние карточки, что хотя бы видно. Сброс строк обнуляет и minsize.

**Обход без пересборки:** двойной клик по ручке под консолью (вернуть логу естественную
высоту) или перетащить её вверх — лидерборд вернётся.

**Вторая половина той же проблемы — мёртвый скроллбар дашборда.** Дашборд обёрнут в canvas,
и его scrollregion обновлялся только по `<Configure>`. Но внутренний фрейм принудительно
зажат до вычисленной высоты, поэтому когда ЗАПРОШЕННАЯ высота контента меняется позже
(появился портфельный график, поздний relayout CTk в frozen-билде), фактический размер — и
значит `Configure` — не срабатывает. Scrollregion застревает размером с вьюпорт: скроллбар
не листается, а сетка давит лидерборд в ноль. Фикс: сторожевой таймер (400 мс) в
`_build_status` сравнивает scrollregion с `winfo_reqheight()` и перекладывает его при
расхождении. Проверено на живом Tk: из застрявшего состояния панель восстанавливается
за один тик.

## 2026-08-18 — «Пропавшая пара» (XLMUSDT): краш-луп воркеров при смене топ-N вселенной

**Симптом.** Периодические диалоги «Unhandled exception in script» с трейсбеком:

```
evolution._winit -> evaluator.build_panel -> evaluator.load_raw
ValueError: no data for ['XLMUSDT'] in data.pickle. Available: [...10 пар...]
```

Выглядело как «при выкачке всех пар одна пара не скачалась».

**Причина.** Скачивание отработало правильно — пара не «потерялась». Вселенная «top-N по
обороту» динамична: между двумя загрузками рейтинг сдвинулся, XLMUSDT выпал из топ-10
(его место занял SUIUSDT). Компонент, у которого остался явный список инструментов со
старым составом (нода/portfolio/rescore/metrics), запрашивал XLMUSDT у нового снапшота —
`load_raw` кидал `ValueError` **в инициализаторе воркера пула**. А `mp.Pool` бесконечно
респавнит воркеров, чей инициализатор умер → вечный краш-луп: диалог на каждый новый
воркер («периодически вылазит») и намертво зависший раунд.

**Фикс** — два слоя:

1. `evolution/evaluator.py::load_raw` — пары, которых нет в снапшоте, теперь **отбрасываются
   с warning'ом** («continuing on the N remaining pairs; re-download data to include them»),
   симуляция продолжается на оставшихся. Ошибка остаётся только если НИ ОДНОЙ запрошенной
   пары нет. Чинит сразу все точки входа: node, portfolio build, rescore, metrics, графики GUI.
2. Страховка от любого другого падения инициализатора (битый pickle и т.п.): `_winit` в
   `evolution/evolution.py`, `alphanode/portfolio_build.py`, `alphanode/rescore_library.py`
   больше не кидает исключение (воркер остаётся жив, ошибка запоминается в `_G['init_error']`),
   а первая же задача воркера падает одним чистым `RuntimeError` → родитель получает его через
   `pool.map` и обрабатывает как обычную ошибку раунда. Вместо вечного респауна — одна
   внятная ошибка в логе.

**Проверка.** На реальном снапшоте пользователя (10 пар без XLM): запрос вчерашней вселенной
с XLMUSDT → warning + 9 пар; полностью неизвестная вселенная → прежний ValueError; точное
подмножество → без изменений.

## 2026-08-18 — Диалог «'NoneType' object has no attribute 'write'» из воркеров пула

**Симптом.** На Windows периодически при работе приложения (portfolio build, rescore)
выскакивал диалог PyInstaller «Unhandled exception in script»:

```
BrokenPipeError: [WinError 232] The pipe is being closed
  (multiprocessing pool.py -> queues.py -> connection.py)
During handling of the above exception, another exception occurred:
'NoneType' object has no attribute 'write'
```

**Причина.** Три звена:

1. `multiprocessing` на Windows спавнит воркеров пула **без наследования std-хендлов**
   (`inheritHandles=False` в `popen_spawn_win32`) — в windowed-билде у воркера
   `sys.stdout`/`sys.stderr` = `None`.
2. В `app_entry.main()` `multiprocessing.freeze_support()` вызывался **до**
   `_fix_std_streams()`. В процессе-воркере `freeze_support()` не возвращается — он сразу
   запускает код воркера, так что до починки потоков дело никогда не доходило.
3. Когда пул закрывается, пока воркер кладёт результат в очередь, возникает безобидный
   `BrokenPipeError [WinError 232]`. `multiprocessing._bootstrap` пытается напечатать
   трейсбек в `sys.stderr` → `None.write` → `AttributeError` вылетает наружу →
   PyInstaller показывает диалог. «Периодически» — потому что это гонка завершения пула.

**Фикс** (`alphanode/app_entry.py`):

1. `_fix_std_streams()` теперь вызывается **до** `freeze_support()` — воркеры пула тоже
   получают живые (или devnull) потоки, и трейсбек от BrokenPipeError тихо уходит в
   devnull вместо диалога.
2. `_fix_std_streams()` укреплён: перед `os.fdopen(fd)` делается `os.fstat(fd)` — на
   мёртвом хендле fdopen может успешно отработать и упасть только при первой записи;
   fstat детерминированно роняет в devnull-фолбэк.

**Важно.** Чинится только пересборкой установщика — фикс в `app_entry.py`.

## 2026-08-18 — UnicodeEncodeError (cp1251) убивал загрузку данных на Windows

**Симптом.** На Windows с русской локалью первый запуск (бутстрап рынка) падал сразу после
приветственного текста:

```
File "fetch_data.py", line 539, in main
File "encodings\cp1251.py", line 19, in encode
UnicodeEncodeError: 'charmap' codec can't encode character '\u2192' in position 20:
character maps to <undefined>
```

То же самое происходило при ручной загрузке всех пар (Settings → MARKET DATA).

**Причина.** Дочерний процесс `--role fetch` пишет прогресс в пайп, который на русской Windows
получает кодировку cp1251. Строка прогресса в `fetch_data.py:539` содержит стрелку `→`
(`\u2192`) — в cp1251 такого символа нет, `print()` кидает `UnicodeEncodeError`, и роль умирает до начала
скачивания. Под ударом были все роли (node, portfolio, forward тоже печатают `→`/`✓`) —
fetch просто срабатывает первым. Читающая сторона (GUI) декодировала пайп той же cp1251,
так что проблема была симметричной.

**Фикс** — три согласованных слоя:

1. `alphanode/app_entry.py` — `_fix_std_streams()` переводит `stdout`/`stderr` замороженного
   процесса на UTF-8 c `errors='replace'`. Чинит все роли frozen-билда разом: непечатаемый
   символ больше никогда не роняет процесс.
2. `alphanode/alphanode_gui.py` — GUI выставляет `PYTHONIOENCODING=utf-8` для детей
   (чинит dev-режим, где дети — обычный python), а все шесть Popen-пайпов (fetch, node,
   metrics, portfolio, forward, pdfreport) читаются с `encoding='utf-8', errors='replace'`.
3. `fetch_data.py` — `main()` ставит `errors='replace'` на свои потоки: голый CLI-запуск
   в cp1251-консоли тоже не падает.

**Проверка.** Локально не воспроизводится (dev-машина в cp65001/UTF-8); краш и оба фикса
проверены принудительной симуляцией `PYTHONIOENCODING=cp1251`: старый код падает с той же
ошибкой, с фиксом печатает нормально.

**Важно.** Пользовательский exe чинится только пересборкой установщика — фикс вшит в
`app_entry.py`.
